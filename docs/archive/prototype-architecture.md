# MeetUp – Application Architecture (Working Document)

## 1. Introduction
This document defines the architecture for a two-application platform centred on social meet-up coordination. App1 is a standalone mobile-first product combining group chat with AI-assisted event planning. App2 is a vendor-facing platform that monetises meet-up intent signals generated by App1 users. The document is a living record — architectural decisions, outstanding questions, and phased scope are updated as the design evolves.

---

## 2. Product Overview

### 2a. App1 — Social Meet-Up Coordination (Standalone)

App1 solves the friction of arranging real-world meet-ups within friend groups. It combines group chat with a lightweight AI-assisted planning layer that surfaces intent, proposes dates, and tracks group availability — without removing the human from the decision.

**Core use cases:**
- Casual catch-ups: *"We haven't seen each other since Christmas, who fancies a night out?"*
- Organised events: *"It's Dave's stag do — we're aiming for Edinburgh, either last weekend of March or first weekend of April."*
- Recurring activities: *"Tuesday run going ahead, coffee in Merchant City after — who can make it?"*

**Key features:**
- Group chat as the primary interface
- AI intent detection — when a meet-up is being discussed, a planning panel appears above the chat
- **Human confirmation loop** — the AI detects and surfaces date references from the conversation; users explicitly confirm availability via "Can make it" / "Cannot make it". Nothing is assumed or auto-assigned.
- **Internal calendar** — an in-app view of confirmed and pending App1 events only. No integration with device calendars, Google Calendar, or Outlook. The SLM can flag potential double-booking against other App1 events.
- Multiple groups per user with varying activity levels (some groups are annual, others weekly)
- Venue mentions in chat are logged and used to build group preference history

**SLM — two distinct roles:**
1. **Language personalisation (on-device):** Learns individual user language patterns and idiosyncrasies (dialect, shorthand, vocabulary) to assist with reply suggestions.
2. **Preference and venue memory (server-side):** Aggregates group venue history across users and devices to surface relevant suggestions when planning a meet-up.

---

### 2b. App2 — Vendor Notification Platform

App2 allows venue owners (coffee shops, restaurants, activity providers) to receive notifications based on meet-up intent signals generated in App1. It operates on a tiered, token-based commercial model. App2 requires App1 to have built meaningful user volume before launch.

**Vendor notification tiers:**

| Tier | Trigger | Cost |
|------|---------|------|
| **Tier 1 — Named mention** | A group explicitly mentions the venue by name in App1 | Free |
| **Tier 2 — Area intent** | A group signals intent to meet in the vendor's area (location + radius + activity type) | Token cost to receive notification + token cost to contact the group |
| **Tier 3 — Competitor intelligence** | A group mentions a competitor venue | Higher token cost — subject to legal and ethical review |
| **Tier 3 — Fuzzy preference match** | A group's venue history matches the vendor's profile | Higher token cost — later phase |

App2 is expected to be a **web portal** for vendor dashboard, offer management, token purchasing, and analytics. Mobile app TBC.

**Value exchange:**
- App1 users benefit from relevant offers and discounts from vendors they are likely to visit
- App2 vendors gain access to known groups of potential customers with expressed intent
- Platform monetises through token sales to vendors

## 3. High-Level Architecture

Three backend paths have been evaluated (see Section 5). The recommended path is **Path B — Supabase**, which provides real-time capability and a sound relational data model from day one without Firestore's lock-in or per-operation cost model.

```
Mobile Client (React Native / Expo)
        │
        ├── Supabase Auth (authentication)
        │
        ├── Supabase (real-time + PostgreSQL)
        │       ├── Realtime subscriptions (chat delivery)
        │       ├── PostgreSQL (all persistent data)
        │       └── Storage (avatars, future media)
        │
        ├── Cloud LLM API (intent & date extraction — App1 v1.1+)
        │
        └── Push Notifications (Expo Notifications → APNs / FCM)
                        │
              [Future: App1/App2 Notification Service]
```

### Backend — Three Paths Evaluated

| | Path A — Firebase + Firestore | Path B — Supabase *(recommended)* | Path C — Custom Stack |
|-|-------------------------------|-----------------------------------|-----------------------|
| **Real-time** | Firestore listeners (built-in) | Supabase Realtime (Postgres-backed) | WebSockets (custom) |
| **Database** | Firestore (document, non-relational) | PostgreSQL | PostgreSQL (Cloud SQL / GCP) |
| **API layer** | None required for PoC | None required (Supabase client SDK) | FastAPI on Cloud Run |
| **Vendor lock-in** | High — proprietary data model, query DSL, SDK | Low — open source, self-hostable, standard SQL | None |
| **Cost at scale** | High — per read/write/delete | Predictable — instance-based | Predictable — instance-based |
| **Relational data model** | Poor — MeetupSessions, VenueDetections etc. require workarounds | Native — full SQL, joins, foreign keys | Native |
| **Offline mobile support** | Mature | Improving (less mature than Firestore) | Manual / none |
| **Migration cost** | High if evolving to production | Low — already on Postgres, real-time layer abstracted | N/A |
| **Verdict** | Throwaway PoC only | Sound from day one — recommended | Correct long-term, more upfront effort |

**Recommendation: Path B (Supabase)**

Supabase provides the speed advantage of the Firebase model (no custom API required for early phases, real-time built-in) without the Firestore data model constraints or per-operation pricing. The entire data model defined in Section 6 works natively as PostgreSQL from day one. As an open-source, self-hostable platform, exit risk is low — migration off Supabase Cloud is a hosting change, not a data model rewrite.

Path A remains valid if the intent is a genuinely throwaway PoC with no expectation of the codebase evolving toward production. This decision must be made explicitly before build starts.

## 9. Development Architecture (Local)

**Path B (Supabase — recommended):**
```
Mobile App (Expo Go / dev build)
        │
        ├── Firebase Auth (hosted — no local emulation needed)
        └── Supabase local (supabase start — Docker)
                ├── PostgreSQL (local instance)
                ├── Realtime server (local)
                └── Supabase Studio (local dashboard)
```
Supabase provides a full local development stack via Docker (`supabase start`), including a local PostgreSQL instance, real-time server, and a Studio UI. No cloud spend during development.

**Path A (Firebase — PoC only):**
```
Mobile App → Firebase Auth (hosted) → Firestore (hosted)
```
No meaningful local emulation of Firestore behaviour — development runs against hosted Firebase project.

## 10. Key Design Principles

- Server is source of truth
- Stateless API design
- Pagination from day one
- Keep AI out of critical path — chat must work without it
- AI detects and surfaces; humans confirm — never auto-assign attendance or intent
- Internal calendar only — no device, Google, or Outlook calendar integration
- Data model must support future App2 features from App1 launch (venue detections, group preference history)
- Design for extension, not over-engineering

---

## 11. Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| Real-time complexity | Supabase Realtime (Path B) provides real-time built on PostgreSQL logical replication — no custom WebSocket layer required. Avoids Firestore lock-in and per-operation pricing. Custom WebSocket layer deferred unless Supabase proves insufficient at scale. |
| Mobile fragmentation | Expo + Firebase Test Lab for real device cloud testing; React Native abstracts most OS differences |
| Scaling chat data | Indexed PostgreSQL + pagination from day one; revisit storage strategy (Cassandra/DynamoDB) if write volume demands it |
| NLP intent detection mis-alignment | Human confirmation loop — AI surfaces dates, user confirms. Bad detections are ignorable, not damaging. Track dismissal rate as a quality signal. |
| AI scope creep | Two SLM roles are architecturally separate. Language personalisation is on-device. Preference memory is server-side. Do not conflate. Use a cloud LLM API for intent/date extraction — do not attempt this with the on-device SLM. |
| App2 GDPR exposure | Chat content analysis for vendor signals requires explicit user opt-in. Must be resolved before any NLP processing of messages is built. |
| Vendor registry abuse | Verification step required before a vendor can claim a venue and receive Tier 1 notifications. Self-registration with a review gate is likely sufficient for early stage. |

## 12. Phased Roadmap

Each phase validates a hypothesis before the next layer is built.

### PoC / MVP
**Hypothesis:** Will users adopt a group chat app specifically for arranging meet-ups?
- **Firebase Auth + Supabase (Path B — recommended)** — real-time built-in, full PostgreSQL data model, open source, local dev stack via Docker
- Alternatively: Firebase Auth + Firestore (Path A) if a genuinely throwaway PoC. Must be decided before build starts — the two paths produce incompatible data models.
- Group chat — create groups, send and receive messages
- User profiles — display name, avatar
- Basic push notifications

### App1 v1.0 — Planning Layer (Manual)
**Hypothesis:** Does explicit in-app meetup planning reduce coordination friction?
- Manual meetup creation — user deliberately creates a planning session in a group
- Propose and vote on dates (manual input, no AI)
- Internal calendar view — in-app only, confirmed and pending App1 events
- "Can make it" / "Cannot make it" attendance responses

### App1 v1.1 — AI Intent Detection
**Hypothesis:** Does AI-surfaced intent detection add value, or do users find it intrusive?
- NLP intent detection via cloud LLM API (e.g. Claude) — detects meet-up discussion in chat
- Planning panel appears above chat when intent detected
- AI surfaces detected date references as chips — user still confirms explicitly
- Intent outputs are structured; model suggestions do not auto-apply without user approval
- Dismissal rate tracked as a quality signal; threshold tuned accordingly

### App1 v1.2 — SLM Personalisation
**Hypothesis:** Does personalised language assistance improve engagement?
- On-device SLM for language personalisation (dialect, shorthand, individual vocabulary)
- Server-side venue/preference memory — group history surfaces relevant suggestions
- Venue detection in chat begins populating VenueDetections table
- Double-booking warning against other App1 events
- Separate SLM responsibilities:
  - intent detection remains a structured inference service
  - local personalization improves suggestion quality and tone
- Prototype a hybrid runtime:
  - lightweight local model or classifier for high-confidence intents
  - cloud fallback for ambiguous messages
- Keep event action execution in app logic, not model output

### App1 v2.0 / App2 Beta — Vendor Platform Foundation
**Hypothesis:** Will vendors register and engage with free-tier notifications?
- Venue registry — vendor self-registration with verification gate
- Tier 1: Free named mention notifications delivered to registered vendors
- App2 web portal (basic) — notification feed, venue profile management
- App1 users see no change — venue detection was already running

### App2 v1.0 — Token Economy
**Hypothesis:** Will vendors pay tokens to act on intent signals?
- Token purchasing and wallet (Stripe integration)
- Tier 2: Area intent notifications (token to receive, token to contact group)
- Vendor offer delivery surfaced in App1 (UX pattern TBD — see Outstanding Questions)
- GDPR consent and opt-in model active for all App1 users

### App2 v2.0 — Advanced Targeting
**Hypothesis:** Is competitor intelligence and fuzzy matching commercially viable?
- Tier 3: Competitor mention notifications (pending legal review)
- Fuzzy preference matching against group venue history
- Vendor analytics dashboard (BigQuery pipeline)
- Subscription tier option for high-volume vendors

## 14. Summary

This architecture delivers a two-application platform built around social meet-up coordination and venue discovery:

- **App1** is a standalone mobile-first product. Group chat is the foundation; AI-assisted planning, venue awareness, and personalisation are layered progressively on top. No feature is on the critical path for chat to function — AI enhances but never blocks.
- **App2** is a vendor notification platform that monetises the meet-up intent generated by App1 users, via a tiered token-based model. It requires App1 user volume to have value.
- The phased roadmap validates each layer before building the next, reducing scope risk and enabling early real-world feedback.
- Outstanding architectural, GDPR, and commercial decisions are tracked in Section 15 with explicit priorities.

## SLM (Small Language Model) Architecture & Principles

This project uses a pragmatic, hybrid SLM design focused on prototyping actionable intent and personalised suggestions while keeping chat fully functional without AI.

Overview
- Goal: detect intents (RSVP, confirm, ask-for-details, propose date) and surface conservative quick-actions that users can apply with a tap.
- Approach: combine deterministic heuristics with a pluggable local runtime and an optional server-side personalization layer.

Runtime Modes
- Heuristic detector: deterministic regex-based detector used as baseline and safe fallback.
- Local runtime: pluggable on-device inference (stubbed in prototype). Interface provides `loadLocalModel()` and `inferIntentLocal(text, userId?)`.
- Server personalization: optional cloud path that stores `user_personalizations` and biases detection/phrasing when enabled.

Data Flow
- Message send → optimistic UI update → analysis step → suggestion UI (or no suggestion).
- Analysis prefers local inference when available, then falls back to heuristic; personalization is read synchronously at analysis time to adjust scoring/phrasing.
- Applying a suggestion maps deterministically to DB actions via `intentActionExecutor` (upsert `event_responses`, confirm events, or open details) — model output never directly mutates data without explicit executor logic.

Personalization
- Stored as `user_personalizations(user_id PK, model_version, preferences jsonb, updated_at)`.
- Prototype preference keys: `preferredReply`, `preferredRsvpPhrases`, `autoAcceptThreshold` (0..1). These are used to adjust detector confidence and suggestion wording only.
- Personalization is strictly optional: baseline functionality works without it.

Privacy & Prototype Stance
- For prototype expedience we assume seeded users have consented; production must implement explicit opt-in, separate telemetry toggles, and deletion endpoints.
- When server personalization is enabled, only structured preferences are stored; raw message text is not persisted for personalization in the prototype.

Integration Points (code)
- `src/intent/intentDetector.ts`: heuristic detector accepts `DetectorPreferences` to bias scoring and phrasing.
- `src/intent/personalization.ts`: read/upsert helpers for `user_personalizations`.
- `src/intent/intentService.ts`: exposes `analyzeMessageIntentWithPersonalization(text, userId)` and legacy `analyzeMessageIntent(text)`.
- `src/slm/localRuntime.ts`: pluggable local inference interface; currently delegates to the detector but includes confidence boost.
- `src/intent/intentActionExecutor.ts`: authoritative mapping from intent → DB actions; conservative and reversible where possible.

Operational Principles
- Keep AI out of the critical path — chat must work if analysis fails.
- Be conservative: suggestions are confirmable and never auto-apply without user interaction (unless an explicit `autoAcceptThreshold` policy is implemented and agreed to).
- Track dismissal/accept rates as quality signals (telemetry gated by consent).
- Version personalization (`model_version`) to allow migrations and staged rollouts.

Next steps for SLM roadmap
- Define and seed realistic `preferences` for test users via the seed script.
- Prototype on-device inference (ONNX/TFLite/Core ML) for lower latency and better privacy.
- Add a small Settings surface to allow editing preferences for prototype users.

### 15c. GDPR, Legal & User Consent Questions

| Priority | Question | Notes |
|----------|----------|-------|
| **P1** | **User consent for chat content analysis** | Tier 1 and Tier 2 both require server-side reading of chat messages to detect venue names and intent signals. Users must be informed and consent must be opt-in. This is a legal requirement, not a UX preference. Must be resolved before any NLP processing of messages is built. |
| **P1** | **Opt-in model design** | Where and how is consent captured? Options: onboarding toggle ("Help local businesses find you"), per-group setting, or app-level setting. Determine the minimum consent scope and how it interacts with E2E encryption decision. |
| **P2** | **Anonymisation and targeting granularity** | Are intent signals shared with vendors at group level or individual user level? Defines the privacy boundary between App1 and App2. Group-level is significantly lower GDPR risk. |
| **P2** | **Data retention policy** | How long are chat messages, intent signals, and venue history retained? Right to erasure (GDPR Article 17) must be supported — what does deletion look like across the data model? |
| **P2** | **Data processor agreements** | Cloud providers (GCP, Firebase) act as data processors. Data Processing Agreements (DPAs) must be in place. Standard clauses exist but must be formally acknowledged. |
| **P3** | **Competitor intelligence — legal and ethical review** | Users are unlikely to expect that mentioning a venue triggers a notification to a competitor. If this tier is built, disclosure must be prominent and specific — not buried in terms of service. Recommend legal review before building. |
| **P3** | **GDPR role classification** | Platform is likely a Data Controller. Vendors receiving signals may be joint controllers or processors depending on what data they receive. This classification affects liability and contractual obligations. Legal review recommended before App2 launch. |
| **P4** | **Children and vulnerable users** | If the platform has no age restriction, COPPA (US) and UK Age Appropriate Design Code may apply. Confirm target user age range and whether any specific protections are required. |
